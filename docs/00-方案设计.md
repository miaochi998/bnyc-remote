# CrossDesk 公司自托管远控方案（v0.2 讨论稿）

> 状态：**讨论稿，未实施**。本文只做方案与决策记录，不含任何真实密钥、密码、令牌。
> v0.2 变更：确认 A2 路线、阿里云改为 203.0.113.10（2C/4G/5Mbps）、账号规模 20、仓库合并为一个 monorepo、Web 纳入验收、账号不统一；新增附录 C/D/E。
> 命名约定：`*.example.com`、`192.0.2.x`、`10.0.0.x` 均为占位符；真实值只记录在本地 `env/real-values.local.md`（不提交、不进 Git）。

## 1. 背景与目标

### 1.1 现状

- 公司已有 **RustDesk 自建服务端**（第三方开源服务端 `lejianwen/rustdesk-server-s6`，含账号系统与地址簿），生产环境稳定运行，员工在用。
- 主要痛点：**Windows 远控 macOS 上不到 4K**（根因另文记录），帧率一般。
- 需求：保留 RustDesk 主线，**新增一套备用远控**，避免单点故障；若更好用则逐步扩大使用面。

### 1.2 目标

1. 新增 CrossDesk 自托管远控，与 RustDesk 并存、互不干扰。
2. 提供**账号 + 地址簿**：每员工一个账号，各自地址簿隔离；设备一次加入，之后一键远控，不再每次输 ID/密码。
3. 同时提供**桌面客户端**与**Web 客户端**两种入口。
4. 局域网内互控**不绕公网**；外网可访问。
5. 可维护：上游版本升级路径清晰，编译/发布可自动化。

### 1.3 非目标

- 不替换 RustDesk；不做多租户、RBAC、审计合规、SSO（首版不做）。
- 不追求 4K 高帧率（4K 仍归 RustDesk；CrossDesk 定位 1080p 办公备用）。
- 不做移动端 iOS/Android 改造（首版只做 Win/mac 桌面端 + Web）。

### 2.2 网络约束（已实测）

| 约束 | 事实 | 影响 |
|---|---|---|
| 80/443 | 公司宽带**入站**被封 | 对外服务不能用这两个端口 |
| 公网 IP | **动态**，双 WAN 1:1，出口 IP 会变 | TURN 的 `external-ip` 会失效，需 DDNS |
| NPM 能力 | 阿里云 Nginx Proxy Manager **只反代 HTTP/HTTPS，不能转 UDP** | TURN 不能经 NPM |
| 端口分流 | 爱快 3.7.24 支持「端口分流」，可把 .10 的指定端口出站强制走 wan1 | TURN 回包可固定线路 |
| 带宽 | 公司 wan1 上行约 100Mbps；阿里云 ECS 约 3Mbps | TURN 只能在公司；阿里云只放信令 |
| 内网 DNS | 当前 DHCP 下发电信 DNS，无内网 DNS | 需 split-horizon；首选爱快「DNS 反向代理」，备选 dnsmasq |
| 认证 | 无 AD/LDAP/SSO | 账号必须自建 |

### 2.3 端口占用

- 已占用：21114–21119（RustDesk）、6504/6506/6508、6520/6521、8000/8001、9000/16662、51820/UDP。
- 新服务可用：**9099/TCP、3478/TCP+UDP、49152–49161/UDP、8443/TCP、8080/TCP**（需最终核对）。

### 2.4 组织约束

- 员工账号上限 **20 个**，每人 **1 台**主用设备；峰值并发远控 **3–4 路**。日常以局域网多机互控为主，员工偶尔外网应急。容量按此规划，不做大容量预留。
- 运维由运维 AI 执行、老板授权；无正式变更窗口，但要求先验证、留回滚。
- **GitHub 只能建公开仓库** → 仓库内容必须脱敏，敏感配置不入库。

## 3. 选型结论

### 3.1 为什么是 CrossDesk

| 维度 | 结论 |
|---|---|
| 成熟度 | 2023 年建仓，7.9k stars，有 Web 客户端、服务端管理台、WSS + Coturn 标准架构 |
| 账号扩展性 | 服务端 C++/SQLite，旁边可挂独立 portal 服务，**不动 LGPL 服务端** |
| 客户端可改造 | 桌面端 C++/Slint 源码开放；Web 端**纯静态 HTML/JS，零编译** |
| 4K | 支持 3840×2160 |
| 中文 | 界面与文档完善 |

### 3.2 为什么不选 Airhand

技术参数更强（120fps、QUIC、虚拟显示器），但建仓仅 26 天、实质单人、协议无兼容层、无账号生态、无官方 4K 实测。**只适合独立 POC，不适合承载公司办公。**

### 3.3 与 RustDesk 的关系

**并存，不替换。** RustDesk 继续承担 4K/主力；CrossDesk 作为第二通道与「浏览器随时可用」的补充。

## 4. 总体架构

### 4.1 三个候选方案

| | A1：信令阿里云 + TURN 公司 | A2：全部公司 + DDNS | B：全部公司 + 阿里云 WG |
|---|---|---|---|
| 信令位置 | 阿里云 ECS | 公司 .10 | 公司 .10 |
| TURN 位置 | 公司 .10 | 公司 .10 | 公司 .10 |
| 内网信令 | 绕阿里云 | **直连** | **直连** |
| 外网入口 | 阿里云固定 IP | DDNS（动态） | 阿里云固定 IP（WG） |
| 阿里云作用 | 信令 | 无 | 隧道 + 固定入口 |
| 依赖 | 拆 compose + 阿里云证书 | 爱快映射 + DDNS | WG 隧道 + 阿里云转发 |
| 复杂度 | 中 | **低** | 高 |
| 适合 | 正式 | **先验证** | 正式（进阶） |

### 4.2 推荐路线

1. **阶段一（验证）用 A2**，分两小步：
   - **P1a 纯内网 IP 验证**：客户端直接填 `192.0.2.10:9099`，不配域名、不碰外网、不改 DNS。先验证 CrossDesk 功能（尤其 Mac 锁屏）与画面质量。**这是最快的 Go/No-Go。**
   - **P1b 域名 + split DNS + 外网**：功能通过后，再上 `cd.example.com` + DDNS + 爱快「DNS 反向代理」+ 爱快映射，验证内外网。
2. **阶段二（正式）升级到 B**：验证通过后，把阿里云 `203.0.113.10` 作为固定入口（WireGuard 隧道），解决动态 IP 与内网直连的兼顾。
3. A1 仅作为「不想动 WG」时的折中，不推荐长期使用。

> 用户已确认：接受 A2；WireGuard 放阶段二；账号 20（每人 1 台）；峰值并发 3–4；Web 纳入验收；CrossDesk 与 RustDesk 账号各自独立；**四个仓库合并为一个 monorepo**（见 9.1）。

| 组件 | 说明 | 来源 | 许可 |

| crossdesk-server | WSS 信令 + 设备注册 + TURN 凭据 | 官方镜像 | LGPL-3.0 |

## 5. 网络设计

### 5.1 域名规划

| 域名 | 解析目标 | 用途 | 证书 |
|---|---|---|---|
| `cd.example.com` | 阿里云（阶段二）或公司 DDNS（阶段一） | 信令 WSS | LE（DNS-01） |
| `turn.example.com` | 公司 DDNS → wan1 公网 IP | STUN/TURN | 不需要 |
| `webcd.example.com` | 阿里云 / 公司 | Web 客户端 | LE |
| `addr.example.com` | 阿里云 / 公司 | portal API | LE |

### 5.2 端口规划

| 端口 | 协议 | 位置 | 用途 | 公网暴露 |
|---|---|---|---|---|
| 9099 | TCP | 信令所在机器 | WSS 信令 | 是（阿里云或爱快映射） |
| 3478 | TCP+UDP | 公司 .10 | STUN/TURN | 是（爱快映射，绑 wan1） |
| 49152–49161 | UDP | 公司 .10 | TURN 中继（**仅 10 个，非 10001 个**） | 是（爱快映射） |
| 8443 | TCP | 阿里云 / 公司 | Web + portal HTTPS | 是 |
| 8080 | TCP | 公司 .10 | portal 内部监听 | 否（仅反代） |

### 5.3 证书

- 全部使用 **Let's Encrypt + DNS-01（DNSPod API）**，不依赖 80/443。
- 证书部署到：信令容器（`certs/` 目录）、nginx/NPM、portal。
- 不使用自签证书，客户端无需导入根证书。

### 5.4 爱快映射与端口分流（阶段一/二通用）

**端口映射（绑 wan1）**：

| 外网端口 | 内网目标 | 协议 |
|---|---|---|
| 3478 | 192.0.2.10:3478 | TCP+UDP |
| 49152–49161 | 192.0.2.10:49152–49161 | UDP |

**端口分流（解决双 WAN 回包错线）**：

爱快 → 流控分流 → 端口分流 → 添加：
- 线路：wan1
- 源地址：192.0.2.10
- 协议：TCP+UDP
- 目的端口：3478,49152-49161
- 启用

### 5.5 DDNS 与 Coturn `external-ip`

- 爱快 DDNS 把 `turn.example.com` 更新为 wan1 当前公网 IP。
- 公司 coturn 所在主机跑 systemd timer（每 5 分钟）：
  ```
  解析 turn.example.com → 与 .env 中 EXTERNAL_IP 比较 → 不同则改写并重启 coturn
  ```
- 注意：IP 变化的窗口期内，已在途的中继会断，P2P 直连不受影响。

### 5.6 内网 DNS（split-horizon）

- **首选：爱快自带的「DNS 反向代理」**（网络设置 → DNS 设置 → DNS 反向代理），添加 `cd.example.com → 192.0.2.10`，再把爱快 DHCP 下发的 DNS 改为爱快自身 `192.0.2.1`。**零新增服务、不改路由表**。
- 备选：在 .10 新装 dnsmasq，配置 `address=/cd.example.com/192.0.2.10`，DHCP 的 DNS 改为 `192.0.2.10`。
- 效果：内网解析到内网 IP（直连）；员工离开公司后 DHCP 获取公网 DNS，自动走公网。
- 说明：这是 **DNS 层面**，不是路由层面——只决定「客户端问谁做域名解析」，不改路由表、网关和上网路径。
- 风险：全员 DNS 依赖爱快（但爱快本就是网关，其故障原本就会断网，不构成新增单点）；租期 120 分钟内离网可能短暂解析失败（可接受）。

### 5.7 内外网访问路径

**阶段一（A2）**
```
内网：客户端 → hosts/split DNS → 192.0.2.10:9099（直连）
外网：客户端 → turn/cd DDNS → 爱快映射 → 192.0.2.10:9099
媒体：ICE 直连优先；失败走 .10:3478 中继
```

**阶段二（B）**
```
内网：客户端 → split DNS → 192.0.2.10:9099（直连）
外网：客户端 → 阿里云 9099 → WG 隧道 → 192.0.2.10:9099
媒体：ICE 直连优先；中继走公司 .10（带宽充足）
```

## 7. 账号与地址簿详细设计

### 7.1 数据模型（SQLite）

```sql
-- 用户
CREATE TABLE users (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  username      TEXT NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,            -- bcrypt / argon2id
  display_name  TEXT,
  role          TEXT NOT NULL DEFAULT 'user',  -- admin | user
  disabled      INTEGER NOT NULL DEFAULT 0,
  created_at    TEXT NOT NULL,
  updated_at    TEXT NOT NULL
);

-- 设备（员工自己的电脑）
CREATE TABLE devices (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id       INTEGER NOT NULL REFERENCES users(id),
  name          TEXT NOT NULL,            -- 如「办公室台式」「家里笔记本」
  remote_id     TEXT NOT NULL,            -- 9 位设备 ID
  secret_cipher BLOB NOT NULL,            -- 设备密码，AES-GCM 加密
  secret_nonce  BLOB NOT NULL,
  note          TEXT,
  created_at    TEXT NOT NULL,
  updated_at    TEXT NOT NULL,
  UNIQUE(user_id, remote_id)
);

-- 审计（可选，首版只记录登录与设备增删）
CREATE TABLE audit_log (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id    INTEGER,
  action     TEXT NOT NULL,
  detail     TEXT,
  ip         TEXT,
  created_at TEXT NOT NULL
);
```

### 7.2 API（首版）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/login` | 用户名密码 → JWT |
| POST | `/api/logout` | 失效 token |
| GET | `/api/devices` | 当前用户地址簿 |
| POST | `/api/devices` | 新增设备（name, remote_id, password） |
| PUT | `/api/devices/{id}` | 修改 |
| DELETE | `/api/devices/{id}` | 删除 |
| GET | `/api/admin/users` | 管理员：用户列表 |
| POST | `/api/admin/users` | 管理员：开号 |
| POST | `/api/admin/users/{id}/reset-password` | 管理员：重置密码 |
| GET | `/healthz` | 健康检查 |

### 7.3 认证

- 密码：argon2id（或 bcrypt cost 12）。
- Token：JWT，HS256，有效期 12h，支持刷新。
- 设备密码：**服务端 AES-256-GCM 加密存储**，密钥来自环境变量（不入库、不入 Git）。
- 传输：全站 HTTPS。

### 7.4 安全要点

- 登录失败限速（IP + 用户名）。
- 管理员操作写审计日志。
- 设备密码只在「下发地址簿」时解密，且仅返回给本人。
- 数据库文件权限 600，备份加密。

## 9. 仓库与版本管理

### 9.1 仓库布局（GitHub 公开，**单个 monorepo**）

四个原有仓库合并为一个 monorepo，目录规划：

| 目录 | 内容 | 说明 |
|---|---|---|
| `docs/` | 设计文档、部署手册、运维手册 | 脱敏后提交 |
| `portal/` | 自研账号/地址簿服务（Go + SQLite + 管理页） | 自研 |
| `web/` | Web 客户端 overlay：`addressbook.js`、`addressbook.css`、注入脚本、上游版本锁定文件 | 不含上游整站 |
| `client/patches/` | 桌面端 fork 的 **patch 集**（不提交完整上游代码） | 见下 |
| `client/build/` | 拉上游 → 打 patch → 构建 → 出包 的脚本 | 保证可复现 |
| `deploy/` | docker-compose、`.env.example`、DDNS/备份/健康检查脚本 | 全部占位符 |
| `.github/workflows/` | CI：构建、gitleaks 扫描、发布 | |

**为什么桌面端用 patch 而不是完整 fork**：CrossDesk 上游仓库约 49MB，完整 fork 会把大量上游代码塞进 monorepo，升级时冲突难以分辨。用 patch 集只保留「我们改了什么」，上游发版时 `clone upstream → git apply patches → 构建`，冲突点一目了然。若后续 patch 变复杂，再考虑独立 fork 仓库。

### 9.2 公开仓库安全策略（**强制**）

**绝对不能提交**：

| 类别 | 例子 |
|---|---|
| 真实网络信息 | 内网 IP、公网 IP、真实域名、端口映射表 |
| 凭据 | 密码、API Token、SSH 私钥、WG 私钥、JWT 密钥、AES 密钥 |
| 证书 | 任何 `.pem` / `.key` / `.crt`（含自签） |
| 数据 | SQLite 库、设备 ID、员工姓名/账号、审计日志 |
| 拓扑 | 完整网络图、设备清单、备份路径 |
| 第三方 | 阿里云 AccessKey、DNSPod Token |

**允许提交**：

- 源码、测试、通用文档

### C.4 5Mbps 下的中继与并发建议

- **阿里云绝不做 TURN**：5Mbps 只够信令 + WG 转发。
- **P2P 优先**：CrossDesk 是 WebRTC ICE，同网段/WireGuard 内直连成功率高，TURN 仅对称 NAT 兜底。
- 5Mbps 理论：1080p 一路约 2–4Mbps，最多 1–2 路；**4K 不可行**。
- 中继留在公司 100Mbps 出口。峰值 3–4 路即使全走中继，1080p 约 8–16Mbps，公司出口充足。

## 附录 D：内网 DNS（split DNS）说明与讨论要点

### D.1 它解决什么问题

阶段一 A2 里，信令在公司 `.10`，客户端填 `cd.example.com`。公网 DNS 把它解析到**公司公网 IP**，于是内网员工访问时会「出门再回来」（hairpin NAT），部分路由器不支持，可能直接连不上。

**split DNS** 就是让内网电脑把这个域名解析成 `192.0.2.10`，内网直接连；员工离开公司后用自己的 DNS，自动解析到公网。

**重要：这不是路由改动。** 它只改「客户端问哪个 DNS 服务器」，不改路由表、不改网关、不影响上网路径。

### D.2 三个选项

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A（首选）** | 爱快自带「DNS 反向代理」：加 `cd.example.com → 192.0.2.10`，DHCP 的 DNS 改为 `192.0.2.1`（爱快自身） | **零新增服务、不改路由**；爱快本就是网关 | 依赖爱快 DNS 功能 |
| B | 在 .10 新装 dnsmasq，加 `address=/cd.example.com/192.0.2.10`，DHCP DNS 改为 `192.0.2.10` | 与爱快解耦、可控 | 新增常驻服务、单点 |
| C | 不做 split DNS | 最省事 | hairpin 风险、内网也绕公网 |

### D.3 关键前提（不满足就无效）

- **必须改爱快 DHCP 下发的 DNS**。当前下发的是电信 DNS，只在爱快里加反向代理、不改 DHCP = 不生效。
- 租期 120 分钟，员工离网后可能短暂仍用内网 DNS（可接受）。
- 可选兜底：内网 DNS 不可达时回落公共 DNS（但会导致内网域名解析到公网，需权衡）。

### D.4 与运维 AI 讨论的 5 个问题

1. 爱快 3.7.24 的「DNS 反向代理」能否添加 `cd.example.com → 192.0.2.10`？是否支持同时正常转发其他域名？
2. 爱快 DHCP 下发的 DNS 改为 `192.0.2.1`（爱快自身）后，会影响哪些设备（NAS、打印、摄像）？是否需要测试窗口？
3. 租期 120 分钟，离网后多久生效？这个短暂失败可接受吗？
4. 要不要配兜底 DNS？兜底会让内网域名解析到公网，接受吗？
5. 改动前如何备份爱快配置与回滚？

### D.5 阶段一可以先不做

P1a 用**内网 IP 直连**（客户端填 `192.0.2.10:9099`），完全不需要 DNS。只有 P1b（上域名 + 外网）才需要 split DNS。所以这一项不影响先验证 CrossDesk。
